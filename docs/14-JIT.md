## 1. 它是什么

一个 **copy-and-patch（复制-补丁）模板 JIT**：

- 每种「opcode + 类型参数 + 小操作数」的原生代码块，**预渲染成模板**缓存起来；
- 编译一条指令 = `memcpy 模板` + 写几处**重定位**（立即数、栈槽偏移、跳转序号、字节码地址）；
- 编译一个函数 = 把指令块**按顺序首尾相接**，再填一张「指令序号 → 块地址」表。

它和「逐条指令现场生成机器码」的传统模板 JIT 的区别在于：**编译期不再跑编码逻辑**，
所以编译成本掉到了「内存带宽」量级 —— 边际 **3.3–3.5 µs/函数**。

它不是基于 LLVM 的 JIT：没有 IR、没有寄存器分配、没有优化管线，因此**没有毫秒级编译**，
代价是生成的代码不做跨指令优化（每条指令的语义直接展开成一小段固定原生码）。

## 2. 怎么用

### 2.1 整程序 JIT（最常用）

```bash
j8c 程序.j8 -o 程序.bc          # 编译成 v3 模块
j8run 程序.bc --jit             # 用 JIT 跑（哪个函数不支持就自动回退解释器）
```

`j8run --jit` 会在运行前编译入口函数；之后每个被 `CALL` 到的函数**首次调用时惰性编译**，
编译失败（例如含 `JMP_IND`）就那个函数回退解释器，其余函数照旧走原生。

### 2.2 字节码里的三条指令

| 指令 | 作用 |
|---|---|
| `JIT_SUBMIT funcIdx, outOff` | 编译**模块内第 funcIdx 个函数**，原生入口指针写进栈槽 outOff |
| `JIT_COMPILE ptrOff, lenOff, outOff` | 编译**任意一串字节码**（指针/长度都从栈槽读），入口指针写槽 |
| `CALL_NATIVE reg, argBaseOff, retOff` | 调寄存器里的**原生**入口 |

`CALL_IND` 的目标是**字节码**地址（要能在函数目录里查到），`CALL_NATIVE` 的目标是**原生**地址
—— 两者互补，合起来才闭环：编译出来的东西客人自己就能调。

### 2.3 手写汇编示例（编译一段内嵌字节码并调用）

```asm
.FUNC main 0 0
  STACK_INIT 4096 64
  STACK_ALLOC 128
  JIT_SUBMIT 1, 0          ; 编译 1 号函数 → 原生入口写入槽 0
  LOAD u64 R0, 0, 0
  PUSH_REG u64 R0
  COUT u64                 ; 打印原生入口地址
  HALT

.FUNC addone 8 8
  STACK_ALLOC 80
  LOAD u64 R0, 0, 8        ; 参数在帧基址 +8
  PUSH_REG u64 R0
  PUSH_IMM u64 1
  ADD u64
  POP_REG u64 R1
  STORE u64 R1, 0, 0       ; 返回值写帧基址 +0
  RET
```

`JIT_COMPILE` 的用法就是先往栈槽里放「字节码指针」和「长度」，再发指令；
典型来源是把一段字节码当数据嵌在程序里（`.BYTE`）或运行期拼出来。

### 2.4 宿主 API

```cpp
VM vm;
vm.module.loadFromFile("程序.bc");
vm.jitCompile(0);                        // 编译 0 号函数，返回原生入口（void*）
void* p = vm.jitCompileBlob(bc, size);   // 编译任意码流（按内容缓存）
```

## 3. 内部结构

### 3.1 模板与重定位

模板按「opcode + TD + 会被编进字节里的小操作数（寄存器号 / mode / 比较子操作）」做键。
**大操作数（立即数、栈槽偏移、跳转序号、字节码地址）不参与键** —— 它们在模板里是空洞，
由重定位在实例化时填。

重定位位置**不用手写**，而是自动发现：

```
1. 把该指令的字节码抄进合成缓冲区，大操作数清 0  → 渲染一次 = 基准模板
2. 把第 k 个大操作数置成全 1，其余仍为 0        → 再渲染一次
3. 两次产物逐字节取差 → 差异区间就是第 k 个操作数的重定位位置与长度
```

「全 1」这个选择有讲究：它保证了**符号扩展**的情况也能被覆盖
（比如 `i8` 的 -1 渲染出来是 `0xFFFFFFFFFFFFFFFF`，差异就是 8 字节，而不是 1 字节）。

### 3.2 块布局：拼接 + 序号表

- 每条指令编成一块，**按指令顺序首尾相接**。
- 于是**顺序执行不需要任何跳转指令** —— 上一条写完直接落到下一条。缺省路径零分派开销。
- 只有 `JMP` / `BRANCH` 需要跳，它们走一张
  **「指令序号 → 块地址」表**：`jmp qword ptr [r15 + idx*8]`。
- 表在发射过程中**逐项填自己的块地址**，所以前向引用也不需要回填 —— 整趟一遍过，
  没有 patch 列表、没有第二趟预扫。

这就是「以指令序号为 computed-goto 索引 + 拼接编译」：
编译到跳转时不需要记任何待回填项，直接继续拼下一段。

### 3.3 寄存器约定（生成的原生码里）

| 寄存器 | 用途 |
|---|---|
| `rbx` | `Thread*` |
| `r12` | 数据栈基址 |
| `r13` | `stackPtr` |
| `r14` | 作用域基址 |
| `r15` | 「序号 → 块地址」表基址 |

- `regs[]` / `scope[]` / `stack` / `stackPtr` 在内存里始终是权威值；
  调用 helper 前 spill、返回后 reload（helper 可能扩容并搬迁数据栈）。
- 只有**会改作用域**的 helper（`STACK_INIT` / `SCOPE_*` / `CALL` / `CALL_IND` / `CALL_NATIVE`）
  才需要在返回后重建 `r14`。

### 3.4 调用

`CALL` **不内联**，而是发射成对 helper `jitCallImpl` 的调用：
压 VM 帧 → 调被调函数的 JIT 版本（没有就回退解释器）→ 弹帧还原。

因此 **JIT 代码里的 `RET` 就是原生 `ret`**，递归不需要额外机制，
而且 **JIT 与解释器可以互相调用**。

`CALL_NATIVE` 走 `jitCallNativeImpl`，帧语义完全一样，只是目标从「函数下标」换成「原生指针」。

### 3.5 产物存放

编译产物进一个**可执行 arena**：`mmap(RWX + MAP_POPULATE)`，块大小 8 KiB 起倍增到 128 KiB 封顶，
函数**紧挨着放**（RWX 时不需要按页取整，否则每个小函数会吃掉 4 KiB 并让预触页开销翻几倍）。
这样每个函数只花一次 `memcpy`，**没有 per-function `mprotect`**。

内核若禁止 RWX（PaX / SELinux 等），自动回退成 `RW + mprotect(PROT_READ|PROT_EXEC)`（保留 W^X）。

## 4. 性能

| 指标 | 数值（Release，连续 3 次自测的范围） |
|---|---|
| 编译一个函数（边际成本） | **3.3–3.5 µs** |
| 冷启动（首个函数，含 arena 首次 mmap） | **~46–50 µs**（波动最大的一项，受系统负载影响） |
| 编译吞吐 | ~35 MB/s 字节码（≈ 165 ns/条指令） |
| **摊薄点** | **≈ 18–19 轮循环** |
| 热循环 1000 万轮 | JIT **11.7 ns/轮** vs 解释器 ~200 ns/轮（**16–17×**） |
| 递归 `fib(27)`（63.5 万次调用） | JIT **63–66 ns/调用** vs 解释器 ~335 ns/调用（**~5.2×**） |

> 复测命令：直接跑 `Jadeight2ReWrite/build-isa3/Jadeight2`（不带参数即执行自测，
> 性能数字随自测一起打印）。上表为 Release 构建下连续三次自测的范围；单次数字会随
> CPU 频率/负载浮动（冷启动一项历史上曾测到 ~25 µs，故按范围给）。

对比参照（同机实测）：CPython 解释一条字节码 ~37 ns、一次函数调用 ~159 ns。
也就是说 **JIT 编译一条 VM 指令的代价（≈165 ns）与 CPython 一次函数调用同量级**。

编译成本的历史（同一基准）：

| 阶段 | 边际成本 |
|---|---|
| 最初「逐条发射 + patch 表 + 每函数 mprotect」 | 15.5 µs |
| 序号表 + 拼接（去掉 patch/预扫） | 6.2 µs |
| copy-and-patch + arena 紧包 + 序列表不清零 | **3.3 µs** |

## 5. 正确性怎么保证

两道自检，都在 VM 自测里跑：

1. **模板 vs 直接发射：逐字节等价**（4 例）。
   同一个函数分别走「模板路径」和「直接发射路径」编译，比对**产物字节 + 块起点表**必须完全相同。
   `emitOne` 一份逻辑同时供两条路径使用（不能有两份真相），任何重定位位置写错都会立刻暴露。
2. **全程序行为等价**。
   `JIT_NO_TEMPLATES=1 j8run 程序.bc --jit` 与开模板跑同一套回归测试，输出必须一致。

另外 `j8c` 的回归测试在**解释器**与 **`--jit`** 两条路径下都跑（各 18 项），输出与期望逐行比对。

## 6. 限制

- **`JMP_IND` 不支持**：它的落点是运行期算出来的，无法静态映射到原生块。
  含它的函数整函数编译失败、回退解释器（其余函数不受影响）。
- **不做跨指令优化**：没有常量折叠、没有寄存器分配、没有内联。
  每条指令的语义按模板展开，优化交给上层编译器（`j8c`）。
- **`JIT_COMPILE` 的码流必须自洽**：它是一段独立的指令流（跳转按函数相对偏移），
  里面的 `CALL` 仍按**本模块**的函数下标解析。
- **J8 源码层还够不到这三条指令**（`j8c` 没有对应内建），目前要从手写汇编发出。
- 产物**不回收**：arena 只增不减，长跑的动态编译场景需要注意（当前按内容缓存，
  同一段码流只编译一次）。

## 7. 复现命令

```bash
# 构建
cd Jadeight2ReWrite && cmake -S . -B build-isa3 -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build build-isa3

# 自测（含编译成本基准与模板等价性检查）
./build-isa3/Jadeight2

# 关掉模板做 A/B
JIT_NO_TEMPLATES=1 ./build-isa3/Jadeight2

# 整程序 JIT
cd ../JadeightCompiler && cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build build
./build/j8c tests/t3_functions.j8 -o /tmp/t3.bc && ./build/j8run /tmp/t3.bc --jit
```
